# 学习与验收方式

每周围绕一个可验证的问题工作。课程解释概念，文档核对接口，论文解释设计选择，实验检验自己的理解。

## 一周如何安排

| 活动 | 预算 | 完成条件 |
| --- | --- | --- |
| 开课前更新 | 0.5 小时 | 核对当前资料、版本和一个相关进展，留下简短记录 |
| 视频、教程与论文选读 | 2.5 小时 | 能用自己的话回答本周关键问题 |
| 实现与正确性检查 | 3.5 小时 | 最小输入、边界输入与参考实现通过 |
| 测量与分析 | 2 小时 | 保存原始数据，解释至少一个观察 |
| 整理报告 | 0.5 小时 | 合并随实验记录的结果，说明何时值得采用、哪里还没验证 |

资源表中的时间是选读预算，不是视频总时长。选读资料替换相应学习时段，不额外叠加。基础不足或环境配置超时就顺延，保留完整验收。

W 编号表示固定单元，学习顺序为 W1～W6 → W13 → W7～W12 → W14～W16；9 小时是初始预算。日历建议预留 2～4 周缓冲，优先用于算子/模型/编译阶段与 W12 恢复实验；先修补课另计。已掌握的内容用证据跳过，未掌握的内容不能靠压缩调试时间补偿。

## 必做与扩展的边界

| 单元 | 最小验收范围 | 基础通过后的扩展 |
| --- | --- | --- |
| W3 | 两种简单 Reduce、一个代表输入的报告 | 多级归约与更多调优策略 |
| W6 | 一个小 Block 的前向、显式 Attention/SDPA 对照和一段时间线 | backward、更多模型与多种后端 |
| W7 | 2 卡 collective 正确性与消息大小曲线 | 4 卡、最小 DDP；训练先修不足时 DDP 移到 W11 |
| W10 | 两条单因素负载扫描、一个调优变量、指标与局限 | HF 对比和更大参数网格 |
| W11 | 1/2 卡固定全局 batch 的 FP32 基线 | 4 卡；另开对照研究 AMP 或输入流水线 |
| W12 | 2 卡 DDP/FSDP2 对照和同 world size 的小模型恢复 | 4 卡、弹性恢复、offload、activation checkpointing |
| W13 | eager/compile 正确性、首次与稳态测量、一个模型区段 | 自定义 Attention 或更多 CS336 子题 |
| W16 | 同资源任务的 FIFO/SJF 仿真和事件日志 | 多 GPU 资源、placement group、真实 GPU 运行 |

最小范围的正确性和复现要求不能降低；时间不足先删除扩展。W12 可分成“分片对照”和“恢复核验”两次完成，保留同一单元编号。

## 学习步骤

1. 读本周问题和 `context.md`，按 [更新流程](weekly-refresh.md) 核对资料，确定版本。写下一条预测，例如“输入增大后，带宽会逐渐接近稳定值”。
2. 打开 [章节导学](study-guide.md)，每段读到指定章节后立即做暂停练习；通过段内检查再继续，遇到具体困难才打开补充材料。
3. 在 `labs/` 下建立实验目录。三段练习共同构成本周项目，先写参考实现与正确性检查，再测量性能，不另建重复项目。
4. 随实验用 [报告模板](../templates/experiment-report.md) 记录环境、配置、数据和解释。最后半小时用于整理，不能等到最后才找原始记录。
5. 将产出链接填入周页面末尾与 [进度表](progress.md)。验收不通过时，记录原因并继续本周。

## 性能实验的共同约定

- 区分正确性运行、计时运行与 profiler 采样；profiler 的额外开销不混入正式延迟。
- 固定输入、dtype、算法语义与精度设置。记录容差，不预设手写版本一定更快。
- GPU 计时要处理异步执行：写明 CUDA Event 或同步边界，区分 kernel 时间与端到端时间。
- 记录预热次数、重复次数、每次原始测量及汇总方式。建议先做 3 组独立测量；组内重复数按算子耗时调整。
- 保留编译、加载、冷缓存的成本，但与稳态结果分别报告。输入分配、数据传输是否计入要明确。
- 记录设备、软件版本、电源状态、其他负载和输入规模。不同设备的绝对值不直接解释为算法收益。
- 未测量值写“未测量”；失败或 OOM 单独记录，不能填成 0 或从报告中悄悄删除。
- 数值对齐与内存/同步检查分别记录；sanitizer 未报错不能证明任意输入都正确。
- 样本很少时将 p95 等分位数标为探索结果，报告请求数、测量窗口与多次运行的离散程度，避免只报一个最佳值。

## 证据与结论的边界

算子表定位热点，系统时间线观察 CPU/拷贝/GPU/等待，kernel 指标解释算子内部行为。先找影响最大的区段，再深入测量，不要求每周同时使用全部工具。

服务实验同时记录计划到达率、实际发送速率、并发上限及是否触顶。并发限制可能反压请求生成器，“配置到达率不变”不能证明服务器收到的速率不变。区分成功请求吞吐、输出 token 吞吐和满足预先定义延迟目标的有效吞吐。

报告区分直接观察、机制推断与未验证假设。缓存开关、精度变化、编译开关和卡数变化分别做对照，避免一次改变多个因素后归因于其中一个。

原始小型 CSV/JSON 与图表可以随 Git 保存；权重、大型 trace 和 checkpoint 放在忽略的 `artifacts/` 或外部位置，在报告中记录来源与生成方法。

## 怎样验收

W13、W10、W12/W14、W16 结束时，再用 [阶段检查](curriculum-design.md) 看这些实验能否一起回答一个完整问题，不增加独立项目。

沿用附件提出的门槛：总分至少 80，正确性至少 16/20，可复现性至少 7/10。附件未给出完整分项，下面是本仓库拟定的分配，并非沿用一份已核验的外部评分表。

| 维度 | 分值 | 证据 |
| --- | --- | --- |
| 正确性 | 20 | 参考对照、边界输入、数值容差或任务语义检查 |
| 原理理解 | 20 | 不看资料解释机制与适用条件 |
| 测量质量 | 25 | 控制变量、预热同步、重复测量、原始数据 |
| 分析与局限 | 25 | 一张有效图表、证据支持的结论、未解决问题 |
| 可复现性 | 10 | 环境、完整命令、配置、数据与结果关联 |

W1 用手算和程序核对代替 GPU 性能测量；调度仿真检查任务是否丢失、资源是否超分配。即使分数达到要求，结果错误、数据缺失或结论没有依据时仍需修正。

## 笔记与文章

笔记保存为 `notes.md`，论文笔记按需用 [论文模板](../templates/paper-note.md)。W3、W6、W8 可将实验报告整理成短文：讲清一个问题，用一张图说明结果，再写出结论和局限。无需另写长篇学习总结。

每段记录实际读到的章节/函数、一个预测、练习入口、检查结果和一个未解决问题。计划中列出的阅读位置不代表已经学完；未核对的视频时间戳保持空缺。
