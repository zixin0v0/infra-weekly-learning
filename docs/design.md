## 顺序怎么调整

完整顺序只在 [课程目录](../course/README.md) 维护。这里说明 W13 提前到 W6 后的原因：先把单卡模型和编译连接起来，再进入集合通信。

W1～W16 保留为固定编号，便于引用已有文件。它们与实际日历周数不必一致；实验没完成，就继续做这个单元。

做过模型时间线分析后，马上比较 eager 和 torch.compile，能更早知道哪些工作值得交给框架。W13 复用已有的小 Block，不依赖 DDP/FSDP2，因此可以提前。

W2～W5 保留小型手写 kernel，用来理解执行和数据搬运。以后处理真实问题时，先用现成库建立参考，再测热点、试编译或配置优化；这些仍解决不了的问题，才考虑定制 kernel。

W7 暂时没有多卡环境时，可以先学 W8～W10 的单卡服务，进度表保留 W7 未完成。开始 W11 前，再补齐训练基础和通信实验。各阶段的具体条件见 [先修检查](../course/prerequisites.md)。

## 学习正文怎样组织

每个单元的入口、讲解、检查与选读分别维护：

| 文件 | 内容 | 怎么用 |
| --- | --- | --- |
| `README.md` | 要解决的问题、所需基础、课表和实验范围 | 从这里进入当前小节 |
| `session-XX.md` | 具体问题、例子、图解、指定材料、练习与核对 | 先理解再动手，做完沿下一课继续 |
| `assessment.md` | 单元变式、排错题与完成要求 | 合上示例检查能否独立完成 |
| `context.md` | 相关设计、来源日期、适用条件与限制 | 基础完成后按问题选读 |

每节先从一个具体问题建立直觉，结合小例子追踪变量、形状或数据，再落到代码、公式与练习。理解所需的解释放在正文，答案可以折叠；不要求机械重复同一套小标题。

结构、内存格、矩阵和时间线用原创技术图说明。图中的输入与正文相同，独立预测题再换条件；理论数字、模拟输入与实测分别标明。图片与导出脚本的职责见 [维护规则](maintenance.md)。

官方英文课程是讲解入口，配中文重点。文档用来核对现在的接口，论文解释设计，项目代码帮助理解实现。有些新方向没有合适视频，读指定文档就够了，不必凑齐所有媒介。

“主流”在这里指选作参考的常用工程做法，并非采用率排名。“前沿”也不等于所有场景里最快的方案：[进展索引](../resources/optional.md) 只列与本周问题有关的候选。像区域编译这样的设计已经存在一段时间，仍然值得学，无需把它称为新突破。

## 怎样看论文与实际使用之间的差距

读到加速数字时，先找出它的条件：什么硬件、什么输入、与谁比较、精度是否相同、哪些成本没有计入。接着再判断自己的实验是否满足这些条件。论文可能已有真实部署；官方项目也可能仍在试验阶段，要看具体内容。

| 论文或示例里的结论 | 还需要追问 |
| --- | --- |
| 某个 kernel 更快 | 输入范围、mask、dtype 和误差是否一致？整个模型也更快吗？ |
| 显存减少 | 是否增加了搬运、重算或额外状态？峰值是在什么时刻测的？ |
| 服务吞吐提高 | 请求分布、实际到达率、失败率和尾延迟怎样？输出质量有没有变化？ |
| 训练扩展性更好 | 全局 batch、更新语义和数据顺序是否保持一致？长期收敛验证过吗？ |
| 可以恢复任务 | 恢复了哪些状态？会丢多少工作？换卡数或节点故障是否也覆盖？ |
| 可以部署使用 | 版本是否容易固定？如何观察故障、升级和回退？谁承担维护成本？ |

context 中的实际问题是可选拓展，最多选一个写进已有报告。其他问题可以注明尚未验证，不必因此增加一套生产系统。

## 四次阶段掌握检查

每单元按“读懂示例 → 补全关键步骤 → 独立实现 → 改变条件 → 解释与排错”推进。段数可增加；各单元 assessment 提供变式、排错题、推导与回看入口，[复习页](../course/reviews.md) 负责连接不同单元。核心能力逐项通过，不能用总分抵消缺项。

阶段掌握检查整理已有实验，不新开项目，也不要求四套成熟系统全部完成。

| 时间 | 使用哪些结果 | 需要得出的结论 |
| --- | --- | --- |
| W13 后 | GPU 实验与小 Block 报告 | 能比较现成库、练习实现和编译结果，区分局部/整体、首次/稳态成本，解释什么时候无需手写 |
| W10 后 | 服务基线、缓存与负载报告 | 输出检查、失败记录和 SLO 有效吞吐齐全，能说明瓶颈在哪里，并保留可回退配置 |
| W12 初查，W14 后掌握检查 | 更新对照、恢复实验和并行切分图 | 能解释省下的显存去了哪里、增加了什么通信；恢复后的状态和下一步行为经过核对 |
| W16 后 | 仿真结果与 Ray 日志 | 任务不丢失、资源不超分配；能区分准入、放置和执行，说明仿真没有覆盖哪些集群问题 |

记录时区分“只设计了”“能运行”“指定条件下可复现”和“接到更大系统后也验证过”。个人的实际状态只在 [进度页](../course/progress.md) 记录。是否能用于生产，需要另行约定运行时长、故障、隔离和维护要求。

W16 四阶段完成后，做 [综合掌握检查](../course/reviews.md#final)：复用训练、服务和调度实验，解释系统结构，诊断 GPU 空闲、吞吐下降、显存不足、恢复不一致，并实际完成适用的小验证；再根据显存、请求分布与延迟目标选择方案，说明什么结果会让自己改变选择。

## 时间如何分配

每单元的预计范围、基础阶段及桥接分开记录，见 [时间安排](../course/guide.md#time-budget)。时间帮助安排日历，不限制材料或知识；以实际困难调整，不承诺固定完成时长。

实验过程中保存命令、数据和观察。相关进展在基础通过后选读；新增必读应说明知识缺口、先修、范围、练习、核对和预计增量。可补充、替换重复材料或拆段；必要知识不必靠删去另一项来换取时间。

设备安排为 RTX 4060 Laptop 8GB 和服务器的 4 张 RTX 4090 24GB。2026-10-04 本机设备查询与有界显存例子已运行，具体数值见知识核验记录；远端设备与多卡链路仍未验证。算子、小模型和单机通信是候选实验范围。具体后端、显存余量、P2P 和工具版本要在使用前确认；针对其他架构的新方法可以先理解设计，不强求本地复现。

## 资料怎么持续更新

首次进入、长期中断或遇到接口变化时，按 [维护规则](maintenance.md) 检查必读材料与本机支持条件，记录在 `docs/audits/YYYY-MM-DD-topic.md`。确定环境后，尽量用同一版本完成实验；中途只处理复现阻塞和事实错误，新论文留到可选拓展。

如果变化影响后续章节或接口，同步修改对应单元和导航。已完成的实验保留当时配置，不能把不同版本的数据直接混在一起。这里安排的是开始学习时共同更新，目前没有后台定时任务。

## 学完之后往哪里走

| 方向 | 适合什么时候继续 | 下一步先补什么 |
| --- | --- | --- |
| Kernel / 编译 | 能指出一个库或编译器尚未解决的热点 | 选一种与设备匹配的 Tensor Core、CuTe 或 Gluon 实验 |
| 推理系统 | 单卡服务的负载与质量检查已经可靠 | 从量化、投机解码、分离式服务中选一个真实瓶颈 |
| 训练系统 | 更新与恢复实验能复现 | Activation checkpointing、并行组合或故障恢复，先选一项 |
| 平台工程进阶 | 已完成 Docker 实操、Kubernetes 配置和事件诊断 | 本地集群运行，再到生产运维、多租户隔离和容灾 |

[六段系统桥接](../course/bridges/README.md) 把进程、网络、容器、数据、存储与资源调度接入原实验。Docker 实际操作是必做，Kubernetes 对象关系、配置阅读、事件诊断是必做；本地集群操作可后续完成，生产运维另定目标。
