**W1 → W2 → W3 → W4 → W5 → W6 → W13 → W7 → W8 → W9 → W10 → W11 → W12 → W14 → W15 → W16。**

主要调整是把 W13 放到 W6 后。做过模型时间线分析后，马上比较 eager 和 torch.compile，能更早知道哪些工作值得交给框架。W13 复用已有的小 Block，不依赖 DDP/FSDP2，因此可以提前。

W2～W5 保留小型手写 kernel，用来理解执行和数据搬运。以后处理真实问题时，先用现成库建立参考，再测热点、试编译或配置优化；这些仍解决不了的问题，才考虑定制 kernel。

W7 暂时没有多卡环境时，可以先学 W8～W10 的单卡服务，进度表保留 W7 未完成。开始 W11 前，再补齐训练基础和通信实验。各阶段的具体条件见 [先修检查](prerequisites.md)。

## 每周除了原理，还要了解什么

每个单元有三份文件，职责如下。

| 文件 | 内容 | 怎么用 |
| --- | --- | --- |
| `README.md` | 本周问题、实验范围和验收 | 开始时确定目标，结束时检查完成情况 |
| `study-guide.md` | 三段阅读与练习，精确到章节、函数或算法 | 读一段，做一段，遇到卡点再补资料 |
| `context.md` | 当前参考做法、一个相关进展、硬件要求，以及实际使用中的难点 | 开课时重查资料，把其中一个问题写进原报告 |

官方英文课程仍是讲解入口，配中文重点。文档用来核对现在的接口，论文解释设计，项目代码帮助理解实现。有些新方向没有合适视频，读指定文档就够了，不必凑齐所有媒介。

“主流”在这里指选作参考的常用工程做法，并非采用率排名。“前沿”也不等于所有场景里最快的方案：[进展索引](../resources/frontier-watchlist.md) 只列与本周问题有关的候选。像区域编译这样的设计已经存在一段时间，仍然值得学，无需把它称为新突破。

## 怎样看论文与实际使用之间的差距

读到加速数字时，先找出它的条件：什么硬件、什么输入、与谁比较、精度是否相同、哪些成本没有计入。接着再判断自己的实验是否满足这些条件。论文可能已有真实部署；官方项目也可能仍在试验阶段，要看具体内容。

| 论文或示例里的结论 | 还需要追问 |
| --- | --- |
| 某个 kernel 更快 | 输入范围、mask、dtype 和误差是否一致？整个模型也更快吗？ |
| 显存减少 | 是否增加了搬运、重算或额外状态？峰值是在什么时刻测的？ |
| 服务吞吐提高 | 请求分布、实际到达率、失败率和尾延迟怎样？输出质量有没有变化？ |
| 训练扩展性更好 | 全局 batch、更新语义和数据顺序是否保持一致？长期收敛验证过吗？ |
| 可以恢复任务 | 恢复了哪些状态？会丢多少工作？换卡数或节点故障是否也覆盖？ |
| 可以部署使用 | 版本是否容易固定？如何观察故障、升级和回退？谁承担维护成本？ |

每周只处理 `context.md` 指定的一个实际问题，写进已有报告。其他问题可以注明尚未验证，不必因此增加一套生产系统。

## 四次阶段验收

阶段验收整理已有实验，不新开项目，也不要求四套成熟系统全部完成。

| 时间 | 使用哪些结果 | 需要得出的结论 |
| --- | --- | --- |
| W13 后 | GPU 实验与小 Block 报告 | 能比较现成库、教学实现和编译结果，区分局部/整体、首次/稳态成本，解释什么时候无需手写 |
| W10 后 | 服务基线、缓存与负载报告 | 输出检查、失败记录和 SLO 有效吞吐齐全，能说明瓶颈在哪里，并保留可回退配置 |
| W12 后，W14 再补充 | 更新对照、恢复实验和并行切分图 | 能解释省下的显存去了哪里、增加了什么通信；恢复后的状态和下一步行为经过核对 |
| W16 后 | 仿真结果与 Ray 日志 | 任务不丢失、资源不超分配；能区分准入、放置和执行，说明仿真没有覆盖哪些集群问题 |

记录时区分“只设计了”“能运行”“指定条件下可复现”和“接到更大系统后也验证过”。目前仍在第一步。是否能用于生产，需要另行约定运行时长、故障、隔离和维护要求。

## 时间如何分配

每单元默认 9 小时：开课更新30分钟，资料150分钟，实现与正确性检查210分钟，测量分析120分钟，整理报告30分钟。环境配置和先修补课另计。

实验过程中就保存命令、数据和观察，最后半小时负责整理。资料更新与报告合计仍占原来的一小时。每周只跟踪一个相关进展；如果新内容值得必读，就写清它替换哪一段，避免越加越多。做不完时先取消选修，再顺延必要实验。

计划中的设备是 RTX 4060 Laptop 8GB 和服务器的4张 RTX 4090 24GB，来自之前的安排，尚未实际检查。算子、小模型和单机通信是候选实验范围。具体后端、显存余量、P2P 和工具版本要在使用前确认；针对其他架构的新方法可以先理解设计，不强求本地复现。

## 资料怎么持续更新

每次开课按 [30分钟更新流程](weekly-refresh.md) 检查官方文档、发布记录和本周的一个观察方向，留下 `refresh-YYYY-MM-DD.md`。确定环境后，尽量用同一版本完成实验；中途只处理复现阻塞和事实错误，新论文留到选修。

如果变化影响后续章节或接口，同步修改对应单元和导航。已完成的实验保留当时配置，不能把不同版本的数据直接混在一起。这里安排的是开课时共同更新，目前没有后台定时任务。

## 学完之后往哪里走

| 方向 | 适合什么时候继续 | 下一步先补什么 |
| --- | --- | --- |
| Kernel / 编译 | 能指出一个库或编译器尚未解决的热点 | 选一种与设备匹配的 Tensor Core、CuTe 或 Gluon 实验 |
| 推理系统 | 单卡服务的负载与质量检查已经可靠 | 从量化、投机解码、分离式服务中选一个真实瓶颈 |
| 训练系统 | 更新与恢复实验能复现 | Activation checkpointing、并行组合或故障恢复，先选一项 |
| 平台工程 | 已理解任务生命周期，需要集群能力 | 把容器交付、队列、监控和故障处理接成一个小系统 |

数据管线、存储、网络、隔离和成本会在相关单元出现；完整部署在选定方向后再展开。这样既能了解实际工作的要求，也能把当前16个单元做完。
