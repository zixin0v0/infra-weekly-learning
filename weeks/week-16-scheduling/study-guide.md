## 1. 不同指标会给出不同的“更好”（50 分钟）

资源定位：[排队指标、FIFO 与 SJF](../../resources/README.md#r-ostep)。

**先读**：[OSTEP 第 7 章 PDF](../../resources/README.md#r-ostep) §7.1 工作负载假设、§7.2 指标、§7.3 FIFO，再读 §7.4 SJF。关注假设被逐个放宽的过程。

**接着想一想**：把教材 CPU 作业替换成自己的逻辑槽位模型，明确它不含 GPU 内核并发、显存装箱或抢占。写出排队时间、周转时间和 makespan 的定义。

**例子与图解：同一轨迹的两种顺序**

单槽位、无抢占、切换开销忽略；A/B/C 同时在 0 到达，真实时长为 6/2/1，FIFO 并列按 ID 排序。

~~~text
FIFO：0 ── A ── 6 ─ B ─ 8 C 9
SJF ：0 C 1 ─ B ─ 3 ─── A ─── 9
~~~

**暂停题**：分别计算每个任务等待、周转，以及平均值和 makespan。

<details>
<summary>核对答案</summary>

FIFO 的 A/B/C 等待为 0/6/8，平均 14/3；周转为 6/8/9，平均 23/3。SJF 按 A/B/C 身份记等待为 3/1/0，平均 4/3；周转为 9/3/1，平均 13/3。两者 makespan 都为 9，忙碌比例均 100%。平均等待下降并不代表总工作量减少或 GPU 利用率提升；这里测的是逻辑槽位模型。

</details>

**动手练习**：给 3 个同时到达、时长不同的任务手排 FIFO/SJF，计算每个任务开始与结束时间。相同总工作量的单槽位、无空闲例子中，两者 makespan 可以一样，平均等待仍会不同。

**检查结果**：不用运行仿真也能核对一个小例子的全部指标。

## 2. 用相同轨迹检验策略和时长先验（30 分钟）

资源定位：[排队指标、FIFO 与 SJF](../../resources/README.md#r-ostep)。

**先读**：重看 §7.4 的晚到达例子；§7.5 STCF 只用于区分抢占与非抢占，不加入实现范围。对“先响应”有疑问时再查 §7.6，它不是服务中的 TTFT 定义。

**接着想一想**：W15 提供真实事件字段；仿真额外区分调度前可知的时长估计与事后实际时长，不能把未来信息偷偷交给普通策略。

**暂停题：晚到与估计错误**

A 在 0 到达、时长 6；B 在 1 到达、时长 1。非抢占 SJF 会在时间 1 打断 A 吗？若 A/B/C 同时到达，但估计时长为 1/2/6、真实时长仍为 6/2/1，按估计排序会怎样？

<details>
<summary>核对答案</summary>

不会打断；A 在 0～6 运行，B 在 6～7 运行，B 等待 5。按估计排序会成为 A/B/C，与前例 FIFO 一样，优势可能消失。实现区分 estimated_duration 与 actual_duration；理想 SJF 才可明确使用真实时长作 oracle。约定同一时间先处理完成、再接收该时刻全部到达、再派发；同优先级按到达时间与 ID 排序。断言 start≥arrival、end≥start、运行槽位≤容量、每个任务只完成一次。

</details>

**动手练习**：固定到达轨迹和容量，实现非抢占 FIFO、理想 SJF 与带估计误差的 SJF；约定并列排序、同一时刻到达/完成事件的处理次序。先单槽位通过手算，再固定多槽位对照。

**检查结果**：无任务丢失、无超分配，日志能重算指标。有限轨迹只能显示长任务等待，不能单独证明持续到达场景下是否饥饿。

## 3. 策略队列怎样接到执行系统（10 分钟）

资源定位：[可行性、可用性与节点选择](../../resources/README.md#r-ray-schedule)。

**先读**：[Ray Scheduling](../../resources/README.md#r-ray-schedule) 的 `Resources` 和 `Scheduling Strategies` 开头，区分自己的待提交队列与 Ray 的节点选择。

**接着想一想**：将仿真的到达、派发、开始、结束映射到 W15 日志。扩展到 Ray 时，提交层只放行策略选中的任务，仍需单独观测 Ray 内部等待；提交顺序不保证开始顺序。

**例子与图解：提交策略与执行系统的边界**

~~~text
作业到达 → 自己的 FIFO/SJF 待提交队列 → 放行/提交 Ray
           policy_wait                 ↓ Ray 内部等待
                                      start → end
~~~

**暂停题**：作业 arrival=0、submit=2、start=3、end=5，分别有多少策略等待、Ray 内部等待、执行和总周转？只按提交顺序能否推出实际开始顺序？

<details>
<summary>核对答案</summary>

策略等待 2，提交后等待 1，执行 2，总周转 5。提交后等待还可能含依赖与启动，不单指节点资源等待。提交顺序不能保证开始顺序，须保存两个事件。主线仿真保留自己的派发/开始约定，真实 Ray 扩展再分解上述时间；不能混报。p95 需写明分位数规则与样本量，长任务等待单独列。有限轨迹没有出现无限等待，不能证明持续短任务到达时绝不会饥饿。

</details>

**动手练习**：主线完成字段映射与报告，比较均值/p95 排队、周转、makespan 和长任务等待；同时记录分配槽位的忙碌时间比例，不把它写成真实 GPU 利用率。实际 Ray 运行另排扩展。

**完成后检查**：结论带工作负载、先验和容量条件，明确仿真与实测。
