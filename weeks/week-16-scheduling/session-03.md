# W16 第 3 段：策略选好了任务，执行系统为什么还让它等？

[本单元](README.md) · [课程目录](../../course/README.md)

自己的队列决定何时提交，Ray 决定提交后怎样执行。两个阶段都可能等待；只看提交顺序，就会把策略选择与实际开始混为一谈。

## 开始前

先通过同一轨迹的仿真检查，继续复用 W15 的事件记录；实际接入 Ray 是后续扩展。

资源定位：[可行性、可用性与节点选择](../../resources/scheduling.md#r-ray-schedule)。

**先读**：[Ray Scheduling](../../resources/scheduling.md#r-ray-schedule) 的 `Resources` 和 `Scheduling Strategies` 开头，区分自己的待提交队列与 Ray 的节点选择。

**接着想一想**：将仿真的到达、派发、开始、结束映射到 W15 日志。扩展到 Ray 时，提交层只放行策略选中的任务，仍需单独观测 Ray 内部等待；提交顺序不保证开始顺序。

## 分两段记等待，才能知道该改哪里

任务到达后，在自己的 FIFO/SJF 队列里等到 submit，这是策略等待。提交给 Ray 后还可能等待依赖、资源和启动，直到 start 才真正开始；这段不能全部称为资源排队。最后从 start 到 end 是本次执行时间。

回看 [Ray 的结果与准入图](../week-15-ray/session-01.md) 和 [S6 的对象关系](../../course/bridges/s06.md)：控制侧作出选择，执行侧负责运行，二者并非同一事件。先把 arrival、submit、start、end 放在一条时钟线上，再做实际扩展，才能与仿真作有边界的比较。

**例子与图解：提交策略与执行系统的边界**

~~~text
作业到达 → 自己的 FIFO/SJF 待提交队列 → 放行/提交 Ray
           policy_wait                 ↓ Ray 内部等待
                                      start → end
~~~

**暂停题**：作业 arrival=0、submit=2、start=3、end=5，分别有多少策略等待、Ray 内部等待、执行和总周转？只按提交顺序能否推出实际开始顺序？

<details>
<summary>核对答案</summary>

策略等待 2，提交后等待 1，执行 2，总周转 5。提交后等待还可能含依赖与启动，不单指节点资源等待。提交顺序不能保证开始顺序，须保存两个事件。仿真实验保留自己的派发/开始约定，真实 Ray 扩展再分解上述时间；不能混报。p95 需写明分位数规则与样本量，长任务等待单独列。有限轨迹没有出现无限等待，不能证明持续短任务到达时绝不会饥饿。

</details>

**动手练习**：完成仿真日志与 W15 日志的字段对应表，并写入报告，比较均值/p95 排队、周转、makespan 和长任务等待；同时记录分配槽位的忙碌时间比例，不把它写成真实 GPU 利用率。实际 Ray 运行另排扩展。

**完成后检查**：结论带工作负载、先验和容量条件，明确仿真与实测。
