## W15：任务、状态与重试

先做 S6 的任务依赖图，自己把 ObjectRef 接到后续 Task，再完成任务记录器和计数 Actor。把远程返回值与普通函数结果对齐，之后再改变资源与重试条件。

**换个条件试试：** 总资源2 CPU，三个独立任务各申请1 CPU；再把第三个改为申请3 CPU。

**找出问题：** Actor 的计数操作超时后重试，如何避免把一次逻辑任务记两遍？

前者最多两个同跑，后者在资源固定时不可行；逻辑准入不保证物理 CPU 使用量。超时不证明第一次没执行，记录 task_id/attempt_id，业务结果按逻辑任务去重或采用幂等写入；对确定性程序错误不要无限重试。回 W15 第二/三段和 S6。

## 用运行结果检查重试

在 [第三段故障练习](session-03.md#retry) 中，让 A 加 3，确认丢失后重放两次；再让 B 加 4，最后重放 A。分别预测无保护和去重后的计数及 A 的返回值。解释进程在效果与去重记录之间崩溃时，当前实现还缺什么。

<details><summary>核对业务 ID 与故障边界</summary>

A 共尝试四次，B 一次；无保护最终为 16，最后 A 返回 16。去重后 A 只加一次，总数为 7，最后 A 返回首次结果 3。单进程字典不保证重启、并发或写入中途崩溃时的原子性；指出持久化与原子提交缺口即可，不把这个练习扩张成生产存储实现。

</details>

## 掌握检查

- [ ] 任务与 Actor 的行为可复现，返回结果正确。
- [ ] 超时后重复效果能复现，去重接口的重复、变参数与失败输入检查通过。
- [ ] 可重建每个任务的等待与执行时间。
- [ ] 能区分逻辑资源分配、显存实际占用与 GPU 实际忙碌。
- [ ] 不将 CPU sleep 或模拟 GPU 令牌的结果称为真实 GPU 利用率。
