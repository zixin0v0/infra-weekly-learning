## 从已经做过的实验出发

用 Ray Task/Actor、对象引用和逻辑资源声明建立可观测执行记录。资源标签服务于调度准入，实际显存、失败和任务状态仍需明确处理。

## 接着想清一个问题

固定计算图可减少重复调度开销，并研究 GPU 通信/执行配合。适合重复结构的问题，动态到达的任意任务队列未必符合假设。

**读哪里**：[Ray Compiled Graph](https://docs.ray.io/en/latest/ray-core/compiled-graph/ray-compiled-graph.html)。页首的 beta 提示与第一个固定 DAG 示例；先辨认静态依赖，再看性能宣称的测量条件。

**来源快照中的状态**：官方文档将 Compiled Graph 标为 beta，API 仍可能变化；不能把它当作普通 Task API 的无条件替代。

**设备条件**：本周 CPU 小任务即可验证语义；GPU 数据通路和通信能力属于后续条件，不能由 CPU 日志外推。

## 真正用起来，还要考虑什么

真实任务执行涉及重试、重复副作用、幂等性、actor 状态与取消；仅有成功路径耗时不足以说明可靠执行。

**选读后可写进报告**：在原任务日志中保留 task_id、开始/结束、结果或失败状态；在报告说明一个带副作用任务重试时怎样避免重复写入。将当前任务结构与静态 DAG 条件对照，不新增执行框架。

## 选读前核对

查 beta/API 状态与支持限制；若没有固定重复图需求，继续使用普通 Task/Actor。
